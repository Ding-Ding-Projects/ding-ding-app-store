# Local history and version restore

## Behaviour

The Local versions surface is protected by a dedicated local-history credential gate. On first use, the user creates a bounded credential; later sessions require it before Activity records, revision metadata, diffs, labels, exports, archives, or restore can be opened. The verifier is encrypted with the operating-system credential vault and only a short-lived in-memory unlocked state exists in the main process. Lock again is available from the Activity surface. This is a local UX gate, not encryption of the snapshots themselves.

The Activity page includes a **Local versions** browser backed by the App Store's isolated local Git repository. It lists at most the newest 200 snapshot commits, showing each commit's timestamp, subject, label, revision identifier, and tracked state files. **View diff** loads a bounded local diff for that revision. **Label** writes a separate append-only metadata commit, so naming a version never rewrites history. The Activity search and inclusive date range filter the revision list as well as operation rows, and a visible-scope toolbar reports selected, shown, and total versions. Checkboxes support click and Shift-click range selection; **Select all shown**, **Invert shown**, and **Clear** never reach outside the current filtered view.

The revision toolbar exports the selected versions, or the filtered view when none are selected, as metadata-only JSON or Markdown. The document declares schema `ding-ding-app-store.history-revisions.v1`, UTF-8/LF encoding, and omission of `snapshotBytes`, `credentials`, and `secrets`; `changedFiles` remains a list of fixed state-file names. **Open versions in VS Code** uses the same reviewed external-editor bridge as other exports. Snapshot bytes, credentials, and arbitrary paths never cross into renderer export content.

Restore is explicit and uses the same native two-key plus full-slider confirmation as other consequential state changes. The selected revision is checked for a complete set of valid JSON snapshots before any write; older two-file revisions remain restorable with documented empty fallbacks for the newer files. The current state is snapshotted first, then App Store-owned settings, installed records, workspace tabs, appearance, schedules, schedule-run metadata, and external-editor preference are replaced together. A forced new restore commit records the result. The replacement is staged in a process-crash-recoverable `restore-transaction` journal: each target and its previous bytes are flushed before an `applying` manifest is published, replacements are applied from the staged files, and startup recovery rolls back any journal left in `prepared`, `applying`, `applied`, or `rolling-back` state before other services read application data. Before the restore commit begins, the journal enters `recording` with the exact expected commit subject; if startup finds that phase, it keeps the restored bytes only when the repository's latest commit matches that subject, otherwise it rolls them back. On a write or commit failure the service attempts to restore every prior file, reports whether that rollback completed, and never claims success when recovery is incomplete. This is a process-crash recovery boundary; power-loss directory-order durability is not claimed. Protected authenticator snapshots/restores are a separate unavailable boundary on the production host: without a reviewed native handle-relative no-follow adapter, the participant returns typed `EUNSUPPORTED` before mutation, hides those revisions as non-restorable, and retains recovery journals for a later safe implementation. The renderer then reloads history, settings, installed records, workspace tabs, appearance, schedules, and the external-editor settings surface through typed bridges before announcing success, so all restored live state is visible immediately and stale autosave drafts are fenced out. The privileged main-process mutation queue serializes renderer saves and scheduled writes with restore; a pre-restore scheduled task is generation-fenced and cannot publish stale run metadata after the restored schedule is loaded. A later restore can therefore undo an earlier restore. User project folders, credentials, Home Assistant vault material, staged update paths, network remotes, and arbitrary paths are never touched.

## Configuration

The protected-history credential is distinct from tab, group, appearance, and School-mode credentials. It is never stored in settings, local Git snapshots, exports, logs, preload responses, or documentation. If the operating-system vault is unavailable, the history surface remains locked and returns an honest unavailable state. School mode suppresses protected history and invalidates any in-memory unlock immediately when the mode becomes enabled or unavailable.

Snapshots live below the main-process application-data directory in an isolated Git repository. The renderer receives typed revision identifiers and bounded diff text only; it never receives the repository path or a Git command. Labels are one-line UTF-8 values from 1 to 80 characters. The version list, diff, label, and restore actions are exposed through dedicated preload IPC methods. Activity search and date controls project onto Local versions, while the revision toolbar keeps its selection independent from operation-row selection. Revision export is intentionally JSON or Markdown metadata only, with schema `ding-ding-app-store.history-revisions.v1`, UTF-8/LF declarations, and omission fields `snapshotBytes`, `credentials`, and `secrets`; the VS Code action uses the typed `history-revisions` record kind. `settings.reload()`, `workspace.reload()`, `appearance.reload()`, and `schedule.reload()` are the explicit in-memory refresh boundaries after restore; the schedule bridge reloads persisted configuration and run metadata rather than returning a cached scheduler status, then re-arms timers and external-source evaluation. Installed records reload through the operations bridge with discovery disabled, preserving the restored application-data snapshot; registry discovery remains an explicit catalog refresh/startup operation rather than an implicit restore side effect. The settings surface remounts so its external-editor preference is read again. A failed reload falls back to the documented defaults or last-good state and shows a notification rather than silently keeping stale values. Snapshot files use fixed names and bounded JSON content; credential vaults, update staging, and managed-update metadata are deliberately outside the snapshot allowlist.

## Failure modes

Wrong or undersized credentials do not reveal verifier details and do not open any history state. Malformed or unreadable encrypted credential records fail closed as unavailable. A locked or restricted request returns an empty/non-mutating result; it never falls through to the existing Git repository. Unlock, lock-again, list, diff, label, archive, export, and restore routes are sender-checked in the main process. Protected revisions may include the authenticator metadata plus OS-bound encrypted ciphertext as a fixed participant snapshot; this material is never exported to the renderer or ordinary history formats. Legacy seven-file revisions remain restorable as ordinary App Store state. Revisions containing the protected authenticator slot are non-restorable on the production host until a reviewed native handle-relative no-follow adapter exists; the participant returns typed `EUNSUPPORTED` before mutation, retains recovery journals, and never risks redirected ciphertext writes.

An absent or unreadable local repository yields an honest empty version list. Malformed or truncated Activity log lines are ignored individually so one damaged append cannot hide the remaining records; an oversized log still fails closed with a bounded error. Unknown, malformed, unreachable, incomplete, oversized, or invalid-JSON revisions fail closed and leave state unchanged. If Git cannot preserve the current state or commit the restore, the app reports the failure; it never claims a restore that was not recorded. If the process stops during file replacement, the next startup validates the fixed-name journal and restores the saved previous bytes before any state service loads them; an invalid journal fails closed rather than accepting arbitrary paths. A renderer save that arrives while restore is active is rejected by the main-process restore barrier, while a pre-restore scheduled operation is either completed before restore or invalidated before it can publish run metadata. Label failures likewise leave the prior label and commits intact, and later snapshots retain existing label metadata.

## Security considerations

Revision identifiers accept only full 40-hex Git commit IDs and are resolved with `shell: false` against the fixed local repository. Git reads and mutations are bounded, network access is disabled by `GIT_CONFIG_NOSYSTEM`/`GIT_CONFIG_NOGLOBAL`, and user/system hooks are disabled for the history repository. Only the seven fixed non-secret state files can be staged or restored; the separate labels metadata is retained for revision display and is never restored as live application state. Restore-journal manifests are capped, require exactly those seven target basenames plus generated staged/previous names, and reject traversal, duplicates, and unknown phases before any replacement. Staged/previous files are flushed before the manifest can direct replacement. Rollback temporary bytes stay inside the journal root and are removed with it during recovery. Labels are length- and newline-bounded before being written to a JSON metadata file. The renderer cannot submit paths, refs, commands, or remote URLs.

## Verification

Focused contract tests assert the typed revision bridge, bounded revision/diff limits, complete non-secret snapshot-file allowlist, credential/staging exclusions, full-ID validation, append-only label commits, before-and-after restore snapshots, durable partial-apply recovery, helper-level recording-phase callback behavior (with the service wiring checking the latest commit subject), manifest size/path/target validation, coordinated reload callbacks for every restored live surface, serialized mutation ordering, scheduler disk reload, stale-run invalidation, the Activity page's date/action/search filters plus diff/label/restore controls, and Local versions filtering, ID-stable Shift-range selection, visible-scope inversion, omission-safe JSON/Markdown output, and typed VS Code export wiring. The current packaged Activity screenshot predates this version browser, so it is not claimed as visual proof for the new controls until a fresh sanctioned hidden-desktop capture is available.
