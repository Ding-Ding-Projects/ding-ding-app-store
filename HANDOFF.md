## 2026-08-07 CI, release, and Pages workflows added (GitHub-hosted runners)

- AGENTS.md previously required an explicitly labelled self-hosted runner for every Actions job. No such runner has ever been registered for this repository (every prior handoff entry going back through this project's history records that as an open blocker). Asked the repository owner directly; they chose GitHub-hosted runners, both because none of the self-hosted alternative was actually available and because self-hosted runners on a *public* repository are a known risk (any pull request could execute code on infrastructure the owner controls). AGENTS.md is updated to match.
- Added `.github/workflows/ci.yml`: `ubuntu-latest`, runs `npm run check` (renderer/main typecheck, root contract tests, both workspace packages) and `npm run build` on push to `main` and on pull requests into `main`.
- Added `.github/workflows/release.yml`: a `test` job gates everything; on success, a `windows-latest` job builds the unsigned Squirrel.Windows installer (`npx electron-builder --win squirrel --publish never`), verifies the produced `Setup.exe` reports Authenticode status `NotSigned` (build fails otherwise), confirms `RELEASES` and a full `.nupkg` exist, and computes a line-count table; a final `ubuntu-latest` job publishes one non-draft GitHub Release tagged `v<version>-<run number>` with those three assets, verified UTC start/completion timestamps, measured end-to-end duration, the line-count table, and the source commit SHA. A failed `test` or `windows-build` job publishes no release.
- Added `.github/workflows/pages.yml`: `ubuntu-latest`, deploys the existing `site/` static documentation site (already self-contained, no CDN/remote assets) to GitHub Pages via `actions/configure-pages` + `actions/upload-pages-artifact` + `actions/deploy-pages`, matching the `homepage` already declared in `package.json`. This is a GitHub Actions Pages deployment (`pages: write`/`id-token: write`), not a self-hosted build job.

## 2026-08-07 Mobile clipping fix for the Pages documentation site

- Found and fixed a real horizontal-overflow bug in `site/assets/app.css`, not a hypothetical one: at a 320px viewport (a real device width, e.g. older/small phones), the page's `scrollWidth` measured 336px against a 320px `clientWidth` — 16px of clipped/overflowing content — verified with a headless Chromium render (`playwright`, `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`) before touching any code. At 375px/390px there was no overflow already.
- Root cause: `#palette-button` (`.text-button`) combined `white-space: nowrap` with "Command palette" plus three `<kbd>` shortcut chips, with no narrow-width accommodation — the same problem the packaged Electron app already solves for its own command-palette hint (`.palette-hint kbd { display: none }` under 820px) but the docs site never mirrored.
- Fix: added a `@media (max-width: 26rem)` rule that hides the `<kbd>` hints and lets the button wrap on very narrow screens; made `.settings-card label` wrap so the language/funny-level rows don't cram; capped `.text-button`/`.search-wrap` to `max-width: 100%` in the existing breakpoint; added a defensive `overflow-x: hidden` as a backstop.
- Re-measured after the fix: `scrollWidth === clientWidth` (zero overflow) at 320px, 375px, and 390px, and a full-page screenshot at 320px confirms the palette button, search box, and settings sliders all render within the viewport with no cut-off text.
- `npm run check` (renderer/main typecheck + 16/16 contract tests) passes; this change touches only `site/assets/app.css`, no app source.

## 2026-08-07 Real local operation history and export

- `docs/features/uninstall.md` and `site/assets/app.js` already promised local operation history before this change; this change makes that promise true rather than aspirational. Added `docs/features/activity-history.md`, `wiki/Activity-History.md`, and a matching `site/assets/app.js` article, and linked all three from their respective indices.
- Local verification: `npm run check` passes (16/16 root contract tests plus the `catalog-contract` and `domain` workspace typecheck/test suites), and `npm run build` (renderer + main + preload) succeeds. No runtime/packaged/headless capture is claimed for this change — only static and build verification.

## 2026-08-07 MD3 native-control styling, and a self-caused encoding bug fixed

- Restyled native OS controls to genuine Material Design 3 in both `src/renderer/styles.css` and `site/assets/app.css`: `select` gets a custom SVG chevron (`appearance: none` plus a `background-image` data URI, since a later `background:` shorthand rule silently strips an already-set `background-image`), `input[type="range"]` gets a custom track/thumb (`::-webkit-slider-thumb`/`::-moz-range-thumb` split into separate rules — Chromium drops an entire comma-grouped selector list when any member is an unrecognized vendor pseudo-element, so a combined rule silently no-ops), and `input[type="checkbox"]` gets a custom box with a checkmark swapped in via `background-image` on `:checked`. The `.super-confirm` danger variant of the range thumb uses `var(--error)`. Verified rendering in headless Chromium in both light and dark themes.
- While pushing this change through the GitHub API (local `git push` was failing in-session with a transport error unrelated to this repo), `HANDOFF.md`, `ROADMAP.md`, `src/renderer/styles.css`, and `site/assets/app.css` were accidentally double-base64-encoded on `main` — the API tool base64-encodes `content` internally, and it was mistakenly given already-base64-encoded text, so the repository briefly held literal base64 text as the "content" of all four files (including the live Pages-served CSS). Caught by fetching the deployed CSS and finding it wasn't real CSS. Fixed by base64-decoding the corrupted repository content once (recovering the original correct text, since the corruption was exactly one extra encoding pass) and pushing that back as raw plain text. Verified after the fix: all four files decode to their real Markdown/CSS content again.
