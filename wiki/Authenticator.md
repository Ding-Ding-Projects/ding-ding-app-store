# Local authenticator registration and entries

> **Status: limited.** This wiki page is generated from the canonical categorized article.

## Behaviour

The Authenticator tab is a real workspace destination in normal mode. It accepts either a canonical `otpauth://totp/` URI or manual Base32 metadata, validates issuer/account fields, SHA-1/SHA-256/SHA-512, 6–8 digits, and a bounded 1–3600 second period, then renders a local QR matrix in-process. The matrix is a representation for the page; no QR image or URI is written to disk. A pairing preview stays in memory until the user enters one current code. Only then does the main process save metadata and ciphertext through the operating-system credential vault.

Saved entries return issuer, account, label, algorithm, digits, period, a label-only group membership, the current code, the next-period code peek, and a numeric countdown. The next code has its own selectable, appearance-targeted code region. At the exact period boundary the renderer promotes that peek to the current display immediately, so it never shows the previous code beside a zero-second countdown while the next main-process refresh is pending. If the renderer misses more than one period, it hides the stale peek instead of presenting an old code as current. The list supports per-entry rename, label-only group assignment, contiguous reorder controls, checkbox selection, native destructive confirmation for single or bulk delete, and metadata-only JSON/CSV/Markdown export. Export records state UTF-8/LF/schema facts and explicitly omits `secret`, `uri`, `code`, `nextCode`, `remainingSeconds`, and `expiresAt`; JSON carries those facts in its envelope, CSV repeats `schemaVersion` and `omittedFields` columns on each row for standards-compatible parsing, and Markdown carries a short metadata line. The optional Visual Studio Code action opens the same redacted content through the existing editor bridge. Codes are calculated in the main process and the renderer receives metadata and code display only. The local vault serializes metadata transactions across vault objects sharing the app-data paths and rolls back a newly published ciphertext if metadata publication fails, so a failed registration cannot leave an orphan secret file or silently replace a prior entry.

This remains a deliberately bounded slice. It does not claim QR image or clipboard import, camera scanning, deliberate secret export, or a full protected-history/restore manager. “Groups” here means only a validated per-entry text label; there are no stable group entities, colours, ordering, collapsed-state records, or group-level bulk actions. Selection supports ordinary checkbox toggles plus Shift-click and Shift+Space visible-range selection; ranges never reach hidden search results, and stale anchors reset after refresh, filtering, or deletion. Ordinary Activity/history exports contain no authenticator secret material because authenticator mutations are not yet recorded as local history events and authenticator files are not in the history snapshot allowlist; delete/rename/group/reorder changes therefore cannot be restored by the history manager yet. These are explicit follow-up boundaries rather than implied by the tab.

## Configuration

URI registration honours issuer, account, secret, algorithm, digits, and period carried by the URI. Manual registration exposes the same parameters and an explicit reveal control; after preparation it shows a grouped Base32 readout beside the local QR and offers an explicit local clipboard copy. URI input is password-masked by default and has its own explicit reveal and local copy actions. The page resets that reveal state when preparing, changing source, or completing a pairing, and clears the submitted secret/URI after success. Registration fields are locked while a preview is active, and a visible discard action cancels that pending identifier and clears the in-memory secret/URI. A registration identifier and pending secret/URI are held only in main-process memory for ten minutes, with a bounded five-attempt confirmation limit and an expiry timer that clears abandoned references.

The operating-system vault is the only persistence route. If safeStorage is unavailable, registration and list access fail closed with a localized explanation; there is no plaintext fallback. The tab uses the app's normal English, playful Hong Kong Cantonese, or bilingual mode and its adjacent regex builder for local search. The command palette reaches the management toolbar for rename, group, reorder, selection, export, and destructive actions; the toolbar still applies the same list search and anchored regex builder. School mode removes the tab, palette entries, route, keyboard activation, and capability at both renderer and main-process boundaries; a live transition clears pending pairings.

The source, algorithm, and digit fields use bounded keyboard-first pickers. Each picker owns its local plain-text query and optional regex state, opens an anchored full regex builder, reports an honest no-match state and nonempty result count, and supports Arrow/Home/End navigation from the filter input or option list, Enter selection, Escape clear-then-close, and focus return to its trigger. The nested builder keeps its pattern and flags synchronized bidirectionally, localizes its copy, uses button type `button`, and stays inside the picker viewport with internal scrolling. Registration semantics are unchanged: source changes clear pending preview and entered secret/URI, and all three pickers close and reject interaction while a pairing preview is active. The period remains a bounded numeric field because it is a free-form 1–3600 second value rather than an enumerated choice.

## Failure modes

Malformed percent encoding, duplicate or unknown URI parameters, issuer mismatches, `hotp` schemes, invalid Base32, unsupported algorithms/digits, control characters, oversized metadata, QR encoder failure, an unavailable vault, a wrong or expired pairing code, duplicate IDs/orders in a tampered metadata file, unknown delete/export IDs, control-character group labels, and vault write failures return bounded localized errors. A QR failure is handled before a pending pairing is published. A system clock outside the supported timestamp range is reported as a clock problem rather than as a wrong code or missing secret. Concurrent saves and metadata-only management writes are serialized; failed metadata publication restores an existing ciphertext or removes a new one, while an unverified rollback reports an uncertain vault state instead of claiming cancellation. If School mode changes or the user discards a pairing while a vault operation is waiting, the generation/cancellation fence rejects publication or removes the just-saved entry before reporting success, and list/export results are discarded rather than returned after the transition.

## Security considerations

Secrets are accepted once for pairing and are never returned from the main-process registration, list, status, QR, confirmation, history, export, notification, documentation, or preload responses. The page may reveal or copy only the still-entered manual or URI value after an explicit user action; stored values are never rehydrated into those controls. The metadata document contains only bounded non-secret fields. Each secret is encrypted by Electron `safeStorage` under an opaque UUID filename. Plaintext fallback, network QR services, remote images, telemetry, and URI/secret logging are not used. The main process rejects unknown renderer senders, strips the test-only timestamp from preview requests, validates the live School-mode restriction, fences every awaited authenticator operation against a live transition, and clears pending secrets on a restriction transition. Preload validators reject unexpected fields such as `secret` or `uri` and require complete success payloads. Electron's single-instance lock keeps one main process as the writer; vault objects in that process share a per-path transaction queue.
